01. AI로 만든 서비스를 실제로 통하게 만들기
오프닝: 이미 움직이는 MVP에서 출발합니다. 처음 사용하는 사람이 핵심 업무를 끝낼 수 있도록 정상 경로와 실패 경로를 함께 점검합니다. 공통 사례는 공고를 읽고 수정 가능한 준비 목록을 저장하는 경험입니다. 이후 등장하는 준비목록 화면은 강연용 설계 예시이며 운영 서비스의 실행 결과가 아닙니다.

02. MVP 다음 단계의 네 가지 질문
강사 소개는 공개 강의 활동과 역할 위주로 짧게 합니다. 구체적인 사내 수치·고객 정보는 넣지 않습니다. 오늘의 목표는 문제 정의를 다시 길게 하는 것이 아니라 현재 결과물의 품질을 높이는 것입니다.

03. 첫 사용자의 계정에서 다시 시작하기
손들기 20초: 내 계정이 아닌 새 계정에서 실제 데이터 업로드부터 저장·재접속까지 해본 팀은? 웃음 뒤에 이 질문을 던집니다. 이 밈은 강연용 자체 제작 문구와 이모지이며 특정 원작 이미지를 복제하지 않았습니다.

04. 완료 경험으로 제품의 품질을 판단합니다
같은 자료로 기존 방식과 MVP를 비교합니다. 예쁜 답변의 평균 점수와 실제 업무 완료율은 다릅니다. 측정 가능한 작업 하나를 고릅니다. 여기서 제시한 지표는 강연용 권장안이며 업계 공통 합격선이 아닙니다.

05. 공고를 읽고, 준비를 마치는 경험
이후 모든 예시는 이 가상 서비스의 설계 시뮬레이션입니다. 실제 고객 성과나 작동 중인 백엔드라고 소개하지 않습니다. 사용자 인터뷰의 맥락은 가설이며 소상공인 3명 관찰로 검증해야 합니다.

06. 입력부터 재접속까지 여덟 가지 상태
각 상태의 다음 행동을 읽어봅니다. 정상 경로만 만들면 실패할 때 고객이 모든 맥락을 잃습니다. 입력 전에는 예시, 오류에는 해결 방법, 처리 중에는 취소와 중복 방지, 다시 열 때는 저장 상태를 제공합니다.

07. 핵심 작업에 집중하는 화면의 구조
이 장표는 자체 제작 와이어프레임이며 특정 제품의 실제 캡처가 아닙니다. 오른쪽 패널을 모두 없애자는 원칙이 아닙니다. 작업에 필수인 입력은 본문, 보조 설명·이력은 선택 패널로 둡니다. 작은 화면에서 순서가 자연스러운지 먼저 확인합니다.

08. 명확하게 읽히는 타이포그래피와 피드백
WCAG 2.2 AA의 대비·대상 크기 규정에는 예외가 있습니다. 디자인 규격과 법적 준수를 혼동하지 않고 개별 서비스에서 확인합니다. 브라우저 확대 200%, 375px 너비, 키보드만 사용한 흐름을 직접 시도합니다.

09. 디자인 방향과 검토 기준을 함께 세우기
Hallmark는 디자인 스킬, Impeccable도 디자인 스킬입니다. 테마나 카드 개수만으로 품질을 판단하지 않습니다. 장식용 소제목·자간 넓힌 라벨·제목 한 단어 강조·상투적 그라데이션·중첩 카드를 줄이고 실제 작업의 위계를 잡았습니다. critique는 사용자 목표·위계, audit는 구현 품질을 점검합니다. 설치·실행 비교 실험은 하지 않았습니다.

10. 반복 가능한 검토 워크플로
gstack은 독립 LLM이나 UI 프레임워크가 아니라 코딩 에이전트 위에서 역할과 검증을 엮는 묶음입니다. 제품 코드 변경 없이 관찰할 때 qa-only를 선택하고, qa나 ship의 수정·출시 범위는 구분합니다. 예시 보고서는 실제 도구 출력이 아닙니다. 실제 수행 여부를 증거와 함께 보고하게 합니다.

11. 동작의 관찰을 구현 명세로 연결하기
사용자가 지칭한 REA와 동일한지 확정하지 않았습니다. 여기서는 morluto/rea만 후보로 설명합니다. MCP 서버와 CLI·조사 스킬을 통해 JavaScript/Electron·네이티브 앱 분석 등을 연결하는 도구입니다. 설치·실행하지 않았습니다. Hopper·IDA 라이선스를 포함하지 않고 에이전트로 전달되는 자료 정책도 별도입니다.

12. 대화의 시작과 끝을 설계하는 Duolingo
Duolingo는 첫 질문을 본 대화와 분리하고, 중간 평가로 사용자 주도권과 혼란을 확인한다고 설명합니다. 후속 제품 글은 자막·Push-to-Talk·통화 후 피드백을 소개합니다. 성과 상승률은 해당 자료만으로 확인되지 않았으므로 제시하지 않습니다.

13. 담당자가 바뀌어도 이어지는 고객의 맥락
Fin 공식 설명은 학습·테스트·배포·분석 주기를 제시합니다. 이관 문서는 설정된 사람 라우팅 대상이 없으면 이관을 제안하지 않는 경우도 설명합니다. 버튼 하나를 그리는 것으로 실제 인계가 완성되지 않는다는 점을 강조합니다. 제공사의 마케팅 우월성 주장은 재인용하지 않습니다.

14. 일상의 불편을 하나의 완료 경로로
PrintPigeon 창업자는 약 3일과 38달러의 Lovable 크레딧을 보고했습니다. 이는 전체 운영비·인건비가 아닙니다. Backchannel의 첫 유료 의사도 자기보고입니다. 핵심은 성공 숫자보다 기존 업무를 끝내는 구체적인 흐름입니다. 우리 팀은 인터뷰·첫 결제·재사용을 각각 따로 검증합니다.

15. 실패를 전제로 한 권한과 복구 설계
Replit은 Jason Lemkin 앱 데이터 삭제와 이후 완전 복구를 공식 글에서 설명했습니다. 이 사례를 모든 바이브코딩 제품의 실패율로 일반화하지 않습니다. 운영 DB 분리, 최소 권한, 복구 동작을 제품의 기본 기능에 포함하자는 교훈입니다.

16. 도구의 이름보다 재사용할 역할을 구분하기
하나의 검사가 모든 품질을 보장하지 않습니다. 테스트 성공은 해당 환경과 시나리오 범위의 결과입니다. AI의 자신감 있는 문장은 증거가 아닙니다. UI 검토와 백엔드 권한 테스트도 구분합니다.

17. 역할별 검토, 하나의 검증 기준
각 검토자에게 다른 체크리스트를 줍니다. 같은 모델 여러 개가 동의해도 독립적인 사용자 증거가 되지 않습니다. 검토자는 수정하지 않고 파일·증거·심각도·재현 절차를 제출하게 하고 통합자가 한 번에 병합합니다. 병렬화는 시간 감소와 토큰 증가의 교환입니다. gstack 같은 역할 묶음은 절차의 참고입니다. 서로 다른 역할이 같은 결론을 냈다는 사실만으로 통과시키지 않고 재현·스크린샷·테스트 결과를 확인합니다.

18. 검토 요청에 증거의 형식까지 담기
QA·보안·성능 검토자에게도 같은 형식으로 보고하게 하고 관점만 바꿉니다. AI에게 실제 사용자처럼 생각하라고 요청한 결과는 합성 의견입니다. 실제 인터뷰 인용으로 발표하면 안 됩니다. 운영 데이터가 아닌 합성 테스트 데이터부터 사용합니다.

19. 실패 경로를 포함한 최소 검증 시나리오
표의 묶인 항목을 분리하면 실패 시나리오 아홉 개입니다: 빈 값, 잘못된 파일, 중복, 오프라인, 시간 초과, 429, 근거 없음, 다른 계정, 프롬프트 공격. 유해 문서는 공격 입력으로 함께 검토합니다. 결제는 공급사별 웹훅·멱등 처리를 따로 확인합니다.

20. 같은 입력으로 변경 전후를 비교하기
Promptfoo는 평가 실행, Langfuse는 호출 추적의 후보입니다. 동일 평가 세트를 모델·프롬프트·검색 버전별로 실행합니다. LLM 판정자는 편향·순서효과가 있어 일부를 사람이 중복 평가합니다. 테스트 세트를 반복 최적화하면 과적합하므로 별도 보류 세트를 둡니다.

21. 출시 판단의 세 가지 기준
안정화의 정점은 오류가 영원히 0인 상태가 아닙니다. 재현 가능한 기준과 관찰·복구 능력이 있는 상태입니다. 신규 버전은 소수 사용자에게 먼저 적용하고 비용·완료율 악화 시 중단합니다. 테스트 통과 범위를 릴리스 노트에 씁니다.

22. 화면과 AI 사이의 업무 규칙
단일 앱이어도 이 책임을 함수·모듈로 나눌 수 있습니다. 처음부터 마이크로서비스로 쪼갤 필요는 없습니다. UI를 예쁘게 바꿔도 권한·예산·데이터 일관성은 서버에서 지켜야 합니다. 모델은 업무 계약에 맞는 결과를 반환하도록 어댑터로 감쌉니다.

23. AI의 제안과 사람·시스템의 책임
페르소나는 AI 도우미의 말투와 검토 관점을 나누는 데 유용합니다. 책임과 권한은 역할별로 명시합니다. 사용자에게는 모델 이름보다 어떤 일이 자동으로 진행되고 어디서 검토할 수 있는지가 중요합니다.

24. 기기와 클라우드를 연결하는 처리 흐름
이 구조는 설계 예시이며 실제 성능 측정 결과가 아닙니다. 기기 추론도 배터리·메모리·배포·QA 비용이 듭니다. 기기 기능이 없다고 핵심 서비스를 잠그지 않고 대체 입력을 제공합니다. 로컬 처리 결과를 서버로 다시 보낸다면 전송 동의와 최소화를 별도로 봅니다. 사진 설명 예시에서는 로컬 처리 가용성을 먼저 검사합니다. Android ImageDescriber.checkFeatureStatus()의 AVAILABLE·DOWNLOADABLE·DOWNLOADING·UNAVAILABLE을 구분합니다. Apple은 SystemLanguageModel.availability와 사용하는 모델의 이미지 지원을 각각 확인합니다. 준비되지 않은 상태에서 클라우드로 자동 전환하지 않고, 전송 대상·목적을 표시하여 사용자가 선택하게 합니다. 전체 완료율과 로컬·클라우드·대체 경로별 완료율을 같이 기록합니다.

25. 온디바이스 AI의 비용과 지원 조건
Apple Speech는 supportsOnDeviceRecognition을 확인하고 requiresOnDeviceRecognition을 지정해야 로컬 경로를 확실하게 선택할 수 있습니다. Android 공식 문서는 기기 내 처리·서버 호출비 없음과 함께 앱 할당량과 지원 제한을 안내합니다. ML Kit GenAI 추론은 전면 앱에서만 허용하며 백그라운드 실행을 지원하지 않습니다. Apple의 조건부 Private Cloud Compute 혜택은 기기 내 무료와 별개라 본강의에서는 혼합하지 않습니다. Apple의 모델 가용성만으로 모든 이미지 기능까지 지원된다고 판단하지 않습니다. Apple 공식 framework는 로컬 모델, Private Cloud Compute, 외부 모델 경로를 구분합니다. ML Kit Image Description 문서는 현재 영어·베타 및 4가지 FeatureStatus를 안내합니다. 한국어 서비스에서 영문 설명의 별도 번역을 붙인다면 그 정확도·전송·비용도 검증해야 합니다.

26. 모델 선택의 기준은 우리 팀의 업무
가격이 낮은 모델을 쉬운 추출·분류에, 복잡한 작업에는 평가를 통과한 모델을 사용합니다. 최신 라인업은 발표 직전에 다시 확인합니다. Gemini Carbon 가격은 11월 30일까지의 한시 가격입니다. 요금만으로 정확도·응답속도를 추정하지 않습니다. 가입형 제품 구독료와 API 청구는 구분합니다.

27. 성공 한 건당 얼마가 드는가
기본 입력의 Sol 기준 계산: 월 1만 작업 × 1회 × 1.1 = 1만1천 호출. 호출당 2000×2/1M + 500×10/1M = 0.009달러. 월 99달러, 완료 8000건이면 성공당 0.012375달러입니다. 재시도 비율은 실패 확률의 무한 재시도 공식이 아니라 추가 호출량 가정입니다. 실제 청구는 사용량 로그와 대조합니다.

28. 품질을 유지하는 비용 최적화 순서
동시 요청은 지연을 줄일 수 있지만 토큰 자체는 줄이지 않습니다. 모든 요청에 여러 에이전트를 붙이면 비용이 증가합니다. 일정 예산 안에서 복잡한 요청만 추가 검토합니다. 캐시·배치 할인 조건은 공급사별로 다릅니다.

29. 도구 연결과 결과 검증의 경계
MCP 현행 명세는 2026-07-28로 확인했습니다. 통신 표준이 보안과 사실성을 자동 보장하지 않습니다. Skills는 최소 SKILL.md와 선택 참조·스크립트 구조입니다. 에이전트의 제안과 실제 실행 사이에 권한·예산·부작용 경계를 둡니다. 특정 프로토콜을 전부 채택할 필요는 없습니다.

30. 산업별로 재사용할 업무 로직
이 장표에서 교육·이커머스·금융 흐름을 우선 비교하고 나머지는 Q&A 또는 부록으로 연결합니다. 오픈소스는 산업 로직의 출발점이며 완제품 보증이 아닙니다. 실제 화면의 권리와 코드 라이선스는 별도입니다. 금융·의료는 판단을 확정하는 경계를 사람이 검토합니다. 5개 사례 상세는 부록에 모두 정리했습니다.

31. 하나의 공고, 세 단계의 완성도
