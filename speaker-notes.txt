01. 고객이 다시 찾는 AI 서비스
시작
오늘은 셀러가 상품 콘텐츠를 만드는 하나의 사례를 끝까지 따라갑니다. 생성 기능 자체보다 입력, 검수, 결제, 실패 복구가 어떻게 이어져야 하는지 보겠습니다. Seller Studio는 강의를 위해 설계한 가상 서비스입니다. 실제 매출이나 사용자 성과를 주장하는 자료는 아닙니다.

02. 차성재
시작
현재 무신사 Core AI PM으로 Agent Chat, GEO, 모두의AI 서비스를 담당합니다. 아주대 AI대학원에서는 MLOps와 LLMOps를, 서울시립대 스마트시티대학원에서는 DataAnalysis와 ML을 강의합니다. 오늘 소개하는 사례는 특정 회사의 내부 구현을 공개하는 내용이 아닌 교육용 설계입니다.

03. Contents
목차
본강의는 약 45분입니다. 첫째, 어떤 고객 문제를 풀지 정합니다. 둘째, 그 사람이 이해하고 끝낼 수 있는 경험을 설계합니다. 셋째, 외부 AI와 결제를 연결하고 장애를 다룹니다. 넷째, 테스트와 비용으로 현실성을 확인합니다. 마지막으로 이를 포트폴리오와 시연에 담습니다. 질의응답은 15~20분, 상세 저장소와 양식은 부록에서 찾아볼 수 있습니다.

04. JD를 제품의 기준으로 바꾸기
1. 문제와 기준
채용공고의 도구 이름을 모아 설치하는 데서 끝내지 않습니다. 셀러 이해, 빠른 구현, 직접 사용, 데이터 판단이라는 요구를 내가 보여줄 수 있는 산출물로 바꿉니다. 목표 공고 여러 개를 같은 방식으로 정리하면 자주 등장하는 역량과 나의 빈칸이 드러납니다. 오늘의 사례는 커머스 PM 관점으로 이 과정을 시연합니다.

05. 셀러의 일은 게시까지 이어집니다
1. 문제와 기준
“AI 영상 생성기”는 솔루션 이름입니다. 고객 문제는 마감 전에 상품에 맞는 광고를 준비하는 일입니다. 도구가 파일을 생성해도 상품 색이 바뀌거나 사실에 없는 기능이 들어가면 다시 일을 해야 합니다. 이 가설을 확인할 때는 최근 광고를 만들었던 실제 과정을 물어보고, 다시 고친 부분과 걸린 시간을 기록합니다.

06. 작게 시작하되 끝까지 연결하기
1. 문제와 기준
아주 많은 업종과 출력 형식을 한 번에 지원하지 않습니다. 먼저 소규모 브랜드의 상품 한 종류와 세로 광고 한 형식에 집중합니다. 첫 유료 가치는 영상 파일 개수만이 아니라 브랜드 규칙과 검수 이력의 재사용입니다. 이 가설은 고객의 반복 사용과 결제 의사로 검증합니다.

07. 한 번의 작업을 여섯 단계로 나누기
1. 문제와 기준
작업 번호는 사용자가 페이지를 닫아도 이어가기 위한 연결점입니다. 공급사 요청 번호와 우리 작업 번호를 따로 기록합니다. 비용 확인과 결과 검수도 하나의 작업 흐름에 들어갑니다. 뒤에서 장애가 발생했을 때 이 여섯 단계 중 어디까지 완료됐는지 다시 찾아오겠습니다.

08. 글로벌 서비스에서 가져올 동작
1. 문제와 기준
공개 화면에서 직접 확인할 수 있는 사실부터 기록합니다. Creatify는 URL과 샘플이라는 두 출발점을 제공합니다. Higgsfield는 결과 예시 옆에 참조 자료를 넣는 영역을 둡니다. 이 화면만으로 내부 기술 구조나 전환율을 알 수는 없습니다. 우리는 시작 부담과 입력 맥락이라는 동작을 우리 문제에 맞게 가져옵니다.

09. REA로 관찰을 명세로 바꾸기
1. 문제와 기준
REA 같은 도구의 목적은 동작을 이해할 증거를 모으는 것입니다. 공개 화면 관찰과 허용된 코드 분석을 구분하고, 본 사실과 가설을 다른 칸에 적습니다. 이번 자료에서는 공개 UI와 문서를 관찰했고 REA를 실행한 결과로 포장하지 않았습니다. 내부 저장 구조나 결제 구현을 알 수 없으므로 우리 설계의 인수 조건을 별도로 만듭니다.

10. 같은 기능도 시작 화면이 달라집니다
2. 경험 설계
왼쪽은 생성 버튼은 있지만 무엇을 준비하고 무엇을 얻는지 알기 어렵습니다. 오른쪽은 입력한 상품 사실과 확인되지 않은 주장을 분리하고 카피 검수를 먼저 제공합니다. 사람 같은 표현은 감탄사를 넣는 일이 아닙니다. 고객이 지금 결정할 수 있게 만드는 정보와 동사를 고르는 일입니다. 저장 완료 같은 약속은 실제 서버 응답과 일치해야 합니다.

11. 문장을 고치기 전에 약속을 고정하기
2. 경험 설계
영어의 AI 말투 패턴 목록을 한국어에 기계적으로 대입하지 않습니다. 실제 고객의 말과 제품 용어를 우선합니다. Humanizer는 편집을 돕지만 사실 검증 도구가 아닙니다. 특히 최신 v4는 구체적 정보를 더할 수 있어, 이 작업의 프롬프트에는 출처에 없는 사실과 보장을 추가하지 말라고 명시합니다. 다음 단계에서 기능 계약과 문장을 함께 검수합니다.

12. 서비스 하네스가 책임지는 일
2. 경험 설계
모델은 문장이나 이미지를 만들지만 누구의 자료인지, 돈을 받아도 되는지, 중복 생성인지까지 자동으로 책임지지 않습니다. 이 강연에서는 그 주변 장치를 서비스 하네스라고 부릅니다. Claude나 Codex의 작업 환경을 뜻하는 에이전트 하네스와도 구분합니다. 뒤의 저장소들은 이 역할 중 일부를 구현하거나 참고할 수 있는 재료입니다.

13. 저장소는 맡길 일로 고릅니다
2. 경험 설계
다섯 개의 저장소를 모두 같은 종류의 하네스라고 부르지 않습니다. 인증 프레임워크, 결제 스킬, 작업 플랫폼, 테스트 도구, 평가 도구입니다. 별 개수는 관심도를 보여주지만 우리 업무에 맞는지 말해주지는 않습니다. 인증 라이브러리를 도입한 뒤에도 워크스페이스별 접근 권한은 직접 설계하고 테스트해야 합니다.

14. 로그인 다음에는 권한이 남습니다
2. 경험 설계
인증은 누구인지 확인하는 일이고 인가는 지금 이 자료에 무엇을 할 수 있는지 확인하는 일입니다. 브라우저에서 버튼을 숨기는 것만으로는 충분하지 않습니다. 두 개의 테스트 팀과 서로 다른 자료를 준비해서 API와 다운로드 링크를 직접 검증합니다. 서명 URL은 발급 시 권한 확인과 짧은 만료를 두고, 발급된 URL의 즉시 회수 가능성은 저장소 방식에 따라 검토합니다.

15. 결제는 서버의 기록으로 확정합니다
2. 경험 설계
고객이 성공 페이지에 도달했는지와 결제가 확정됐는지는 다릅니다. 웹훅은 중복되거나 순서가 바뀔 수 있습니다. 이벤트 ID뿐 아니라 주문에 대한 지급의 유일성도 지켜야 여러 이벤트가 같은 지급을 반복하지 않습니다. 잔액 숫자만 덮어쓰지 말고 지급, 예약, 사용, 반환 기록이 남는 원장을 둡니다. 결제 사업자의 서비스 국가와 사업자 적격성은 실제 도입 전 확인합니다.

16. 재시도 전에 기존 요청을 찾습니다
2. 경험 설계
영상 공급사는 요청을 받았지만 우리 서버가 응답을 놓칠 수 있습니다. 이때 무조건 다시 제출하면 비용과 결과가 중복됩니다. 먼저 공급사 요청 번호로 상태를 조회합니다. 요청 번호 자체를 받지 못했고 공급사가 멱등 키나 조회 수단을 제공하지 않으면 안전하게 자동 재시도한다고 보장할 수 없습니다. 모호한 상태를 별도로 두고 재조정하거나 운영자가 확인합니다.

17. 실패한 화면에도 다음 행동이 있어야 합니다
2. 경험 설계
대기 중이라고만 쓰기보다 무엇을 기다리는지 알려줍니다. 서버가 진척도를 모르면 70퍼센트 같은 가짜 숫자를 만들지 않습니다. 결과 확인 중과 제작 실패는 다릅니다. 실패가 확정된 경우에만 크레딧 반환을 약속한 정책대로 표시합니다. 상태를 몇 번 바꿔 보고 고객이 어떤 버튼을 눌러야 하는지 설명할 수 있는지 확인합니다.

18. MCP로 제작 도구를 연결합니다
3. 생성과 운영
MCP는 에이전트가 도구를 부를 수 있도록 연결하는 인터페이스입니다. 연결 자체가 고객 서비스의 권한이나 예산 정책을 만들어주지는 않습니다. Claude의 첨부 파일이 자동으로 Higgsfield에 전달된다고 생각하지 말고 공식 업로드 경로를 확인합니다. 문서상 MCP와 CLI는 제작자 계정의 크레딧을 사용하므로 실행 전 잔액과 비용을 확인합니다. 한시적 프로모션은 별도 조건입니다.

19. 고객 서비스에는 API 경계를 둡니다
3. 생성과 운영
제작 도구에서 편하게 만든 실험을 고객 트래픽에 바로 연결하면 계정과 비용이 섞입니다. API는 별도 계정과 잔액을 사용하고 서버에서 키를 보관합니다. 영상 생성이 끝났다는 응답을 받은 뒤에도 파일을 내려받아 보관하는 작업이 남습니다. 결과 보관과 사용량 확정을 재시도 가능하게 만들어야 사용자가 나중에 다시 다운로드할 수 있습니다.

20. 연결 방식마다 맡길 일이 다릅니다
3. 생성과 운영
스킬은 작업 방법과 지침을 주고, MCP는 도구를 연결하고, API는 서비스가 요청을 주고받는 계약입니다. Creatify의 공식 영상 광고 스킬을 MCP라고 잘못 소개하지 않도록 구분했습니다. Stripe는 오래된 로컬 패키지 대신 현재 공식 MCP와 플러그인 문서를 기준으로 설명합니다. 브라우저 에이전트가 우연히 통과한 클릭은 지속적인 회귀 테스트와 다릅니다.

21. 서킷브레이커는 실패의 확산을 막습니다
3. 생성과 운영
Closed는 회로가 연결되어 요청을 보내는 상태, Open은 회로가 끊겨 보내지 않는 상태입니다. 장애가 반복되면 무의미한 호출로 비용과 대기열을 늘리지 않고 잠시 차단합니다. 이후 소수의 시험 요청이 성공하면 다시 열어줍니다. 사용자에게는 입력이 보존됐고 새 생성만 잠시 멈췄다는 사실을 보여줍니다. 입력 오류나 권한 거절은 공급사 장애 표본에서 제외합니다.

22. 재시도·차단·한도는 함께 설계합니다
3. 생성과 운영
서킷브레이커 하나만으로 서비스가 안전해지지는 않습니다. 전체 대기 시간을 제한하는 데드라인, 팀별 자원 격리, 예산을 먼저 예약하는 규칙이 함께 있어야 합니다. Polar의 사용량 기록도 제품의 사용량 차단을 대신하지 않으므로 우리 서비스에서 입장 제한을 구현합니다. 실패했다고 더 비싼 모델로 자동 교체하는 것도 미리 동의한 정책이 없으면 피합니다.

23. 복구의 기준은 원장과 작업 상태입니다
3. 생성과 운영
실패 메시지를 예쁘게 바꾸는 것만으로는 이 문제를 해결할 수 없습니다. 결과를 찾아 연결할 수 있는 식별자와 원장이 있어야 합니다. 비용은 예약과 확정을 분리해 중복을 피합니다. 공급사의 결과와 우리 기록이 다를 때 주기적으로 대조하는 정합성 작업도 둡니다. 기존 요청을 찾을 수 없는 모호한 경우에는 반환이나 재생성을 자동으로 단정하지 않습니다.

24. Claude와 Codex는 같은 명세를 봅니다
4. 검증과 수익
어떤 모델이 더 낫다는 순위가 목적이 아닙니다. 한 모델이 구현하고 다른 모델이 검토할 때도 같은 명세와 커밋을 보고 있어야 합니다. 서로 다른 브랜치의 화면과 코드를 검토하면 합의가 의미 없어집니다. 고객 문제, 데이터 계약, 인수 조건을 문서로 남기고 변경 후 테스트 증거와 함께 검토합니다.

25. 좋은 요청에는 검증 방법이 들어갑니다
4. 검증과 수익
대상과 사실을 먼저 적으면 문장 편집이 기능 약속을 바꾸는 일을 줄일 수 있습니다. 필요한 상태를 미리 명시하면 성공 화면만 완성하는 것을 피할 수 있습니다. 검증 방식도 요청에 넣습니다. 결과 보고에는 무엇을 확인하지 못했는지가 있어야 다음 사람이 작업을 이어갈 수 있습니다.

26. 고객이 겪을 순서로 테스트합니다
4. 검증과 수익
각 테스트는 기대 결과가 선명해야 합니다. “잘 동작한다” 대신 원장에 지급이 한 번만 있는지 확인합니다. Playwright trace는 클릭과 화면을 연결하고, 서버 로그는 데이터와 외부 요청의 상태를 연결합니다. 화면 테스트만으로 권한이나 과금의 정합성을 증명할 수 없으므로 두 증거를 함께 남깁니다.

27. 예쁜 결과에도 틀린 정보가 있습니다
4. 검증과 수익
